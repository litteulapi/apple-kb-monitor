# "Apple Keyboard" System Settings module (KCM)

The author's request: "I want everything properly integrated with KDE Linux".

The module appears in **System Settings → Input & Output → Keyboard → Apple Keyboard**
(KDE category `keyboard`, next to "Keyboard" and "Shortcuts"). The System Settings search finds it
with "apple keyboard", "battery", "fn", "keys", "batteries", "eject", "rename"… From the command line:

```sh
kcmshell6 kcm_applekeyboard                 # standalone window
kcmshell6 kcm_applekeyboard --args keys     # opens the Keys tab (state, keys, notifications, name, diagnostics)
systemsettings kcm_applekeyboard            # inside System Settings
```

![The module in System Settings](../kcm/captures/systemsettings-module.png)

## Why a small C++ plugin (and not a pure QML package)

Checked on the workstation (Plasma 6.7.5, KF 6.30, Qt 6.11) on 2026-10-01:

* `kpackagetool6 --list-types` knows no KCM package structure (only
  `KPackage/Generic`, `KPackage/GenericQML`, `Plasma/*`, `KWin/*`, `KSysguard/SensorFace`) and
  `/usr/share/kpackage/kcms` does not exist: the Plasma 5 "KPackage KCM" format is gone;
* the 103 modules of `kcmshell6 --list` are all `.so` plugins from
  `/usr/lib/qt6/plugins/plasma/kcms/systemsettings/`;
* `KQuickConfigModuleLoader` (libKF6KCMUtils) loads a module through `KPluginFactory`, then its
  QML from the plugin resources (`qrc:/kcm/<id>/main.qml`); the CMake macro
  `kcmutils_add_qml_kcm` (KF ≥ 6.0) compiles `ui/` into those resources.

So a plugin is required. It is kept to a minimum: `kcm/src/kcm.cpp` (the
`KQuickConfigModule` class: load / apply / defaults cycle). The whole interface is
in QML (`kcm/ui/`) and **every read or write goes through the daemon** on the session bus
(`kcm/ui/Store.qml`, QML module `org.kde.plasma.workspace.dbus`, like the widget): the module
opens no file and starts no program itself.

Interface `com.agenceapi.AppleKbMonitor1.Settings` (object `/com/agenceapi/AppleKbMonitor1/Settings`,
`apple-kb-monitord/src/config_api.rs`):

| Method | Role |
|---|---|
| `GetConfig() → s` | JSON `{"values": {…}, "revision": "…", "path": "…"}` (`path`: the config file read): only the module's 10 keys (`alerts.*`, `battery.chemistry`, `notifications.*`, `display.apple_percent`, `apple.will_shutdown`); sections belonging to other programs (`ddc`, `mqtt`, `monitor`, `brightness`) are never read or returned |
| `SetConfig(key, json_value, revision_read) → s` | writes **one** key from the list, value validated (bounds, type), refused with the D-Bus error `com.agenceapi.AppleKbMonitor1.Error.Conflict` if the file changed since it was read; only the key's line changes (comments, line endings, other sections byte for byte), a form that cannot be edited safely = refusal without writing; atomic write, permissions kept (0600 for a new file), a symlinked `config.toml` is written through to its target; returns the new revision |
| `RunAkmctl(args_json, timeout_ms) → s` | runs `akmctl` without a shell, **closed list**: `doctor --json`, `selftest --json --no-save`, `keys --json`, `keymap kde-apply`, `set param <name> <value> --persist` with the names and ranges of `akmctl set param` (`KERNEL_PARAMS`: `fnmode`, `iso_layout`, `swap_opt_cmd`, `swap_ctrl_cmd`, `swap_fn_leftctrl`), `rename --device-name=<valid name> --check\|--yes`; anything else = `AccessDenied` |

The key editor uses `…1.Keymap` (`SetKey`, `SetPreset`, `Apply`, `Reset`), renaming uses
`SetAlias`, reconnection uses `…1.Link`.

Build dependencies: `cmake`, `extra-cmake-modules`; at run time: `qt6-base`,
`qt6-declarative`, `kcmutils`, `ki18n`, `kcoreaddons`, `kirigami`, `libplasma`,
`plasma-workspace` (QML `org.kde.plasma.workspace.dbus`, the data layer of `kcm/ui/Store.qml`;
already present on any Plasma 6). The PKGBUILD declares them and installs:

| Installed file | Role |
|---|---|
| `/usr/lib/qt6/plugins/plasma/kcms/systemsettings/kcm_applekeyboard.so` | plugin + QML pages |
| `/usr/share/applications/kcm_applekeyboard.desktop` | generated by kcmutils (`NoDisplay` launcher, KRunner search) |
| `/usr/share/locale/<lang>/LC_MESSAGES/kcm_applekeyboard.mo` | translations (19 languages) |
| `/usr/share/doc/apple-kb-monitor/KCM.md` | this document |

Standalone build (without a package):

```sh
cmake -S kcm -B /tmp/kcm-build -DCMAKE_INSTALL_PREFIX=/usr -DKDE_INSTALL_USE_QT_SYS_PATHS=ON
cmake --build /tmp/kcm-build
```

## Contents

| Tab | What it shows / does | Source |
|---|---|---|
| **State** | name (alias), model, address, connection; battery: keyboard's indication, Apple display, estimated charge with range and chemistry, voltage, remaining time, battery date; signal (quality + gap in dB), age of the last measurement (updated every second without re-reading), firmware (version, latest known, status), daemon version | D-Bus `GetState` (JSON schema 1), `DaemonVersion` property, `StateChanged` signal |
| **Keys** | effective F1-F12 / Eject table for the current Fn mode (evdev code, Qt key, bound KDE action); Fn mode 0-4, `swap_opt_cmd`, `swap_ctrl_cmd`, `swap_fn_leftctrl`, `iso_layout` with the "ALL Apple keyboards" warning; manual mapping (apple / fkeys / linux-pc presets, adding and removing keys, install, back to the kernel); "Bind F4 to the application launcher" | `akmctl keys --json` (with KDE actions) and D-Bus `.Keymap.KeyTable` in parallel; `.Keymap.Keymap/SetKey/SetPreset/Apply/Reset` (D-Bus only); `akmctl set param NAME VALUE --persist`; `akmctl keymap kde-apply` |
| **Notifications** | battery alerts (enabled, thresholds, critical, re-arm, a single reminder when PowerDevil already warns), battery chemistry, Apple display, connection and new-battery notifications, **WillShutdown**; values shown as the file stores them, daemon bounds and types (thresholds 1-99, critical 0-99, decimal re-arm 1-20), warning for a value the daemon does not take as is | `~/.config/apple-kb-monitor/config.toml`, saved by the System Settings **Apply** button |
| **Name** | alias on this computer (rename, go back to the keyboard's own name); name stored in the keyboard: shown, and **written** by "Write the name into the keyboard…" (confirmation dialog "Write “X” into the keyboard's memory?", then `akmctl rename --device-name=<name> --yes`); "Check (nothing written)" runs the same command with `--check`; the result is shown in the page; the clean forget remains a command to copy (`akmctl repair --force`) | D-Bus `SetAlias(mac, name)`, `keyboard.device.name_on_keyboard` from `GetState`, `akmctl` through D-Bus `Settings.RunAkmctl` (closed command list, argument array, no shell; 60 s deadline) |
| **Diagnostics** | `akmctl doctor --json` (verdict + findings), `akmctl selftest --json --no-save`, "Reconnect", "Copy the diagnosis" (state + table + results, for a ticket), link to TROUBLESHOOTING.md | `akmctl`, D-Bus `.Link.Reconnect` |

### Writes and authentication

No write without an explicit click. **Only one write goes into the keyboard itself**: the stored
name, from the Name tab ("Name in the keyboard" row below).

| Action | Path | Authentication |
|---|---|---|
| `hid_apple` parameters (Fn mode included) | `akmctl set param … --persist` → `pkexec akm-helper` | existing polkit action `com.agenceapi.AppleKbMonitor.set-fnmode`, `auth_admin`: **one password prompt per changed parameter** (the policy deliberately refuses `_keep`) |
| Install / remove the mapping | D-Bus `.Keymap.Apply` / `.Reset` → `pkexec akm-helper install-keymap` | existing polkit action `…install-keymap` |
| Preset, profile keys | D-Bus `.Keymap.SetPreset` / `.SetKey` (the user's `keymap.toml` file) | none |
| Bind F4 | `akmctl keymap kde-apply` (the user's KDE shortcuts, an existing shortcut is never replaced; undo: `akmctl keymap kde-apply --undo`) | none |
| Alias | D-Bus `SetAlias` (BlueZ `Alias`) | none |
| **Name in the keyboard** | "Write the name into the keyboard…" → one confirmation → `akmctl rename --device-name=<name> --yes`: pre-flight, backup of the current name, **one frame written into the keyboard** (register `0x55`) through the hidraw node under the daemon's HID lock, read-back. "Check (nothing written)" = same command with `--check` (nothing is written). See [RENAME-KEYBOARD.md](RENAME-KEYBOARD.md) | MTU read through `pkexec akm-helper hid-inspect --mac <MAC>` (action `com.agenceapi.AppleKbMonitor.hid-inspect`, `allow_active = yes`: no password in the active local session), for the write as well as the check |
| Notifications | D-Bus `Settings.SetConfig`; the daemon writes `config.toml` atomically (`write_atomic`): only the keys **the user changed** are rewritten; every other line keeps its bytes (sections of other programs, comments, LF/CRLF line endings, missing final newline). Comments *inside* a value rewritten over several lines (array) are not kept. Refusal, file intact: unreadable file (too large, permissions, I/O, invalid UTF-8), modified since it was read, or a form the editor does not rewrite (`[[table]]`, inline table, quoted key, multi-line string) | none |
| Start / restart the daemon | `systemctl --user start` / `try-restart apple-kb-monitord.service` | none |

Fn mode goes through `akmctl set param fnmode N --persist` (run by the daemon's `RunAkmctl`)
and not through the D-Bus method `Device.SetFnMode`: that method also takes 0-4 but does not write
`/etc/modprobe.d`, so the setting would be lost on reboot. It is the same polkit action. Once the
new mode is in effect, the module also calls `Device.SetFnMode N` on the connected keyboard: the
value is already in place, so no password is asked, and the daemon remembers it for the next
reconnection (`reapply_settings`) and emits `PropertiesChanged` (widget). The only
D-Bus API added for the module is the `…1.Settings` interface (`GetConfig`, `SetConfig`,
`RunAkmctl`) described above.

The daemon reads `config.toml` at startup: after **Apply**, the module offers
"Restart the service".

## Responsiveness: no I/O on the GUI thread

The "Not responding" incident came from synchronous D-Bus calls without a timeout. Here
(`kcm/ui/Store.qml`):

* D-Bus: asynchronous calls only, through the module's `BusCall` (`kcm/src/buscall.cpp`,
  `QDBusConnection::asyncCall` with the call's own timeout, so QtDBus's 25 s default never
  cuts a longer deadline); daemon presence through `DBusServiceWatcher` (no polling);
  every call has its own deadline (reads 5 s, commands 20-60 s, authenticated writes
  120 s), after which the page says "no answer in time" and a late reply is ignored. A
  parameter write still waiting for polkit is also confirmed by re-reading `KeyTable`
  every 2 s (`kcm/tests/store_timeouts.sh`, which also runs `BusCall` with a 27 s answer);
* commands: run by the daemon (`RunAkmctl`, on a worker thread, killed at their deadline,
  bounded to 1-180 s);
* file: read and written by the daemon (`GetConfig` / `SetConfig`);
* the received JSON is parsed in QML (a few KiB); an invalid or missing answer is shown
  as an error with "Try again", without blocking or emptying the other tabs.

Daemon missing: banner "The keyboard service (apple-kb-monitord) is not running: every setting is
read and written by it…" with the **Start the service** button (the State tab shows "No data…"); without it nothing is shown or set (it reads and writes every setting).

## Languages, themes, accessibility

* Source strings in English, `i18n()/i18nc()/i18np()` (domain `kcm_applekeyboard`, the
  same as the plugin identifier: that is what kcmutils gives the QML context); 19 complete
  catalogs `kcm/po/<lang>/kcm_applekeyboard.po` (every message translated; `ctest`
  checks them all, test `kcm_translations`).
  `akmctl doctor --json` gives an `id` for the verdict and, for each finding, an `id` and its
  values (`args`): the module translates the verdict, the text and the fix from
  those identifiers (`DiagPage.qml`, `findingText`/`findingFix`), never from the English
  sentences; an unknown identifier (newer akmctl) shows the text as is. The
  commands in the fixes stay as they are. `akmctl selftest --json` gives each check a `msg`
  identifier and its values (`args`): the module translates the lines the same way
  (`selftestText`); quoted journal lines, paths and errors stay as they are.
  Update: `kcm/Messages.sh`; check without changing anything: `kcm/Messages.sh --check`.
* Theme colours and fonts (Kirigami, `org.kde.desktop`): light and dark without specific
  code; sizes in `Kirigami.Units` (HiDPI); checked at `QT_SCALE_FACTOR=2`.
* Keyboard only: Tab / Shift+Tab between controls, Ctrl+PgDown / Ctrl+PgUp and Ctrl+Tab /
  Ctrl+Shift+Tab to switch tabs (tested by `tests/e2e/kcm.py`, scenario `actions`); the
  diagnostics buttons stay focusable during an operation (focus is not lost).
* Screen reader: `Accessible.name` / `description` on fields, lists and buttons; a
  row of the key table is a single element ("F1 (Brightness −): alone … ; with fn …").

Scenarios of `tests/e2e/kcm.py`: `screens` (5 tabs in French, State in English, dark
theme, Keys at 2×), `actions` (diagnostics with the keyboard only, Ctrl+Tab, rename refused by the
fake daemon and shown, alerts turned off then **Apply** → `config.toml` contains
`enabled = false`), `systemsettings` (module in System Settings, search for
"battery"), `absent`, `slow` (every method answers after 40 s), `error`, `garbage` (invalid
JSON), `akmctl_slow` (`akmctl` answers after 40 s). Fails if a QML error shows up in
the log, if a passive look causes a write (`SetAlias`, `Apply`, `Refresh`,
`systemctl`, `akmctl` other than `keys`/`keymap show`…), or if the GUI thread is blocked for more
than 100 ms.

Responsiveness measurement: with the module argument `heartbeat` (test hook, inactive otherwise), a
16 ms QML timer (`kcm/ui/main.qml`) writes its largest delay to the log every 500 ms
(`akm-heartbeat {…}`, read with `QT_FORCE_STDERR_LOGGING=1`); that is the time
during which the window could neither paint nor answer the compositor's ping. The X11 ping
`_NET_WM_PING` cannot be used here: Qt does not answer it without a window manager (measured
under Xvfb, even with `_NET_SUPPORTED`).

Results of 2026-10-01 (Qt 6.11.2, KF 6.30, Plasma 6.7.5, Xvfb, llvmpipe software rendering),
last full run: 8/8 scenarios passed; maximum GUI thread delay 12-13 ms on
each of the 5 tabs, in English, in dark mode and at 2×; 13 ms with the daemon missing, in error, invalid
JSON, `akmctl` answering in 40 s; 18 ms with the daemon answering in 40 s; maximum gap between
two heartbeats 513-516 ms (for 500). Over seven runs of the "slow daemon" scenario: 18, 25,
29, 33, 38, 39 ms and **once 101 ms**, at the moment when the three 5 s timeouts expire
together and the error banners appear (first paint of those elements in software
rendering): to be watched; the test threshold stays at 100 ms.

## Known limits

* Writing the name stored in the keyboard goes through `akmctl`: the module never talks
  to the keyboard itself. The name travels as a single argument (`--device-name=<name>`), without a shell or
  terminal; the daemon only accepts `--device-name=<name>` validated by `akm_core::devname`. The clean forget (`akmctl repair --force`) is only shown, to be copied.
* One changed `hid_apple` parameter = one authentication (`auth_admin` policy).
* Notification settings apply when the daemon restarts (button offered).
* The module shows the first keyboard described by `GetState`; several keyboards
  will need a selector.

# Parity with Apple: what is sent to the keyboard, and nothing more

Decision of the manager: implement the functions Apple's system calls for this keyboard (A1314, PID `0x0256`), **only** what Apple really sends, with the same bytes and in the same context. Sources: `RE-PILOTE-MACOS.md`, `RE-PILOTES-ANCIENS.md`, `RE-MACOS-SILICON.md`, `RE-GHIDRA-IOBLUETOOTH.md`, `RE-GHIDRA-KEXT.md` (branch `re/ghidra-kext`).

## The model: Apple's behaviour as one state machine (#251)

`akm-core/src/apple_model.rs` is a pure module (no I/O, injected clock) that reproduces what the macOS 26.5 driver (`IOBluetoothHIDDriver` / `IOAppleBluetoothHIDDriver` / `AppleBluetoothHIDKeyboard`, plus `bluetoothd`) does with this keyboard. All durations, thresholds and counters are in **one** table, `apple_model::APPLE`, each field citing its source; `read_policy`, `machine` and the daemon's actor take their decisions from it. Tests are in `akm-core/src/apple_model/tests.rs` (one conformance test per rule, full scenarios on a simulated clock, proptest properties) unless stated.

Properties (proptest, 512 random sequences of connections, sleeps, requests, outcomes, inputs): never an emission while the breaker is open, never two requests less than 1 s apart, never more than one disconnection request per connection, never an impossible state (`AppleModel::check`).

**Beyond Apple, kept on purpose**: the daemon also reads `0x46` / `0x49` (voltage, #180) and once per connection `0x4F` / `0x60` (#219) in the same burst, under the same breaker and spacing; a 3 s budget per routine burst (four requests 1 s apart: `0x47`, Input `0x30`, `0x46`, `0x49`); a `Refresh()` floor of 5 min (#206); outside the daemon (CLI) a read still requires a key press in the last 60 s.

**Modelled but not emitted on Linux** (no new HID emission): SET_PROTOCOL is made by the kernel/BlueZ (the readiness is the first acquisition); the 3.5 s wait is the kernel's HIDP timeout (the model's watchdog is applied when classifying); Apple's re-read of `0x47` on a state change is not made. GET Input `0x30` **is** requested since #251 (`HIDIOCGINPUT`, one id), so both halves of the read can fail and count.

**Deviation**: after a disconnection asked by the breaker, BlueZ reports reason *Local*, which `recovery.rs` treats as a quiet episode: first page after 5 min, then the slow cadence (`recovery::breaker_disconnection_is_a_quiet_episode`). Apple's `bluetoothd` only re-pages HID devices at a power-state change; the keyboard reconnects by itself on a key press.

## What is deliberately not implemented

* **Name stored in the keyboard (`0x55` `LongDeviceName`, #248).** Prepared (validation, backup, frames, dry run: `akmctl rename --device-name`), registered as the named operation `DeviceName`; the frame is **established byte for byte** [désassemblage] (`RE-NOM-PROPRE-E1.md`: Lion 10.7.5 sends one SET Feature `0x55` of 65 bytes, `0x55` + UTF-8 name + `0x00` padding, then an HCI remote name request; macOS 26.5 never writes the name). The real write stays behind **three locks** (`[apple] allow_device_name_write = true`, default false; control-channel MTU ≥ 66 read on the live socket by `akm-hid-control inspect`; the name typed again) because the firmware's HANDSHAKE and the persistence across a battery change are not measured. See `RENOMMER-CLAVIER.md` §4-6.
* `0x4A` (SCO link state, #216), `0x44` `FullFactoryDefault` (Lion's forget; macOS 26.5 sends `0x41` instead, #217), `0x45`, `0x50`-`0x54`, `0xD0`-`0xFB`, `0x09` (#171), `0xD5`: forbidden or out of scope. The register map refuses them.
* Not simulated by `AppleModel` but **under its breaker** (R3, #251): HID_CONTROL SUSPEND / EXIT_SUSPEND (#244, `akm-hid-control`, which reads the published `breaker.state`), `0x41` `RecantConnection` (forget) and `0x55` (name) through `hidraw::WriteDoor` (same verdict). Out of scope: `0x50`-`0x54` writes, `0x4A` (SCO). Apple's text commands (`ForceBatteryPercent`, `BatteryUpdateInterval`, `HIDControl n`...) and the 1.6 s input filter at wake (dead code in 26.5) are not cloned.

## What can be written, and how

* Class `WriteApple` + named operations (`registry::WriteOp`): `Shutdown` = Feature `0x40` (id only), `DeviceName` = Feature `0x55` (exactly 64 data bytes; real write behind three locks), `Forget` = Feature `0x41` (id only, `akmctl repair` only). `registry::check_write` accepts only these ids, `check_write_op` only the ids of the given operation; the test `only_the_ids_of_the_named_operations_are_writable` sweeps the 256 ids in the three directions and compares with the list of the operations.
* `registry::WriteSession` allows each id once per session, refuses another operation's id and any length but the operation's exact one; `session_authorises_each_id_once_with_its_exact_length` sweeps the 256 ids for every operation.
* `hidraw::hid_write_feature(fd, op, report)` is the only function that issues `HIDIOCSFEATURE`, sized for **one** byte: an operation that carries data (`DeviceName`) can never pass it. Every byte is logged on stderr (`[hid-write] ...`) before the ioctl; a source scan (`this_build_has_one_write_path`) fails if another file names a write ioctl. `hidraw::WriteDoor` is the same door opened by a short-lived `akmctl` command under the HID lock shared with the daemon.
* HID_CONTROL (#244) is a separate program and a separate path: `akm-hid-control` can emit only `0x13` or `0x14` (`HidControl` enum + `check_byte`; the test `only_0x13_and_0x14_pass_the_256_sweep` sweeps the 256 values), one `send` of one byte per keyboard, on the single connected L2CAP socket of `bluetoothd` whose peer is the keyboard and whose PSM is `0x0011`; `this_file_has_one_write_path` fails on any other write call. Before the byte, the daemon's published breaker (`breaker_state::verdict`) must allow it (R3, #251).
* Reads: `hidraw::hid_read_feature` (`HIDIOCGFEATURE`, class `SafeRead` / `OncePerConnection`) and `hidraw::hid_read_input` (`HIDIOCGINPUT`, class `SafeReadInput` = `0x30` only) are the two GET doors, one `ioctl` call (`hid_get_report`); `only_input_0x30_reaches_the_input_ioctl` sweeps the 256 ids. Apple context: RE-GHIDRA-KEXT §2.4 notes that macOS emits `0x14` directly only for HID devices handled in user space; under BlueZ the keyboard is one (`uhid`), so both bytes are sent.
* All tests use a spy (`FeatureSink`) or an invalid descriptor (`-1`): no test ever writes to a real keyboard.

## Effect and risk

The effect of `WillShutdown` on the keyboard is not observable without writing (RE-PILOTE-MACOS §8): Apple's expected gain is a clean sleep without reconnection attempts during the shutdown. Risk: low (production traffic of macOS). To opt out: `[apple] will_shutdown = false`.
